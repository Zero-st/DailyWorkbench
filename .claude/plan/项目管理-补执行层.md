# 项目管理体系重建 · 补齐执行层

## Context

用户问「我的项目管理是不是没做好——具体安排、每天工作进度、完成度」。盘完全仓后的诊断：

**治理层过剩，执行层缺位。** 已有 28 条稳定编号的需求台账 + 演进史、15 篇编号连续的 ADR（含 0010 修订 0001 的闭环）、四阶段路线图带门性、自评打分刻度、预注册放弃线（含项目级）、使用量埋点尺子——这套东西多数团队没有。但：

| 实测证据 | 数字 |
|---|---|
| `.claude/plan/` 计划文档中**零勾选框、零状态字段**的 | 22 / 24 篇 |
| 提交里带周次/任务号的 | ~9 / 112 条 |
| `docs` 类提交 vs `feat` 类提交 | 33 (29.5%) > 26 (23.2%)，非新功能占 60% |
| 两个脉冲日（08-28 / 09-20）贡献的提交占比 | 36%（W37 整周仅 14 条） |
| 计划「排了没执行且 17 天无人发现」 | `next-steps-dogfood-w1.md` 第 2 步（09-03 → 09-20） |
| 上一份周追踪表回填率 | `复盘-dogfood冲刺-W1.md` **0 / 7** |

**所以"完成度"现在算不出来，因为没有分母**：台账的 ✅🔧🚧 是需求状态不是工作量，计划是散文不是可验收条目。

**已向用户说明的顾虑（用户已拍板重建，不再重复）**：本项目已出现「治理产出挤占本体产出」的迹象，再加体系有变成"第 25 篇计划文档"的风险。因此本方案的护栏是：**沿用仓内既有分工模式只新增 2 个文件、所有指标从现有数据算出不引入工时估算、并给机制本身预注册放弃线**（与 ADR 0015 让尺子受自己约束同理）。

**用户已定的三项**：范围＝完整体系 · 每日进度写进产品自己的复盘框（不新建日志习惯）· 作战板归 `.claude/plan/`。

## 二 · 完成度的三个定义（都不靠估算，全从现有数据算）

这是对「完成度怎么算」的直接回答——**一人项目的完成度不该来自工时估算，该来自门禁计数**：

| 层级 | 公式 | 数据源 | 当前值 |
|---|---|---|---|
| **当期完成度** | 出口门禁勾选数 / 总数 | 作战板 | 待建（冲刺 W0-E 有 6 条门禁可直接搬） |
| **需求完成度** | ✅ 条数 / (总数 − ✂) | 需求台账 §4 汇总表 | **15 / 22 = 68%**（已有数据，只是从没人算过） |
| **周门通过率** | 通过的周门 / 已过周数 | [复盘-dogfood冲刺-W2-W4.md](docs/planning/复盘-dogfood冲刺-W2-W4.md) 已有 4 个门 | 0 / 0（W1 09-23 才开始） |

对外只报第一个。

## 三 · 落地清单（8 步）

### 步骤 1 · 新建操作指南（规则，长期）
**`docs/guides/项目管理-操作指南.md`**

沿用 [项目自评打分-指南.md](docs/guides/项目自评打分-指南.md) ↔ [复盘-项目自评打分-2026-09.md](docs/planning/复盘-项目自评打分-2026-09.md) 的「指南定规则 / 载体存数据」先例。内容：

1. 三层节拍：**日**（复盘框一句话，≤30 秒）· **周**（周五 15 分钟仪式，扩现有的）· **期**（冲刺末对表，接自评卡）
2. **统一 DoD（完成的定义）**——一条任务勾 `[x]` 必须同时满足：① 代码/文档已落盘并 commit ② 跑过 `docs/开发测试规范.md` 的对应档位门禁 ③ 作战板那行写了一句可验证的验收事实 ④ 若改了需求状态，台账+演进史已回写。**四条缺一不得勾。**
3. 任务行格式与状态符号：`[ ]` 未开 · `[~]` 在做 · `[x]` 完成 · `[-]` 放弃（必须写一句为什么）
4. 完成度三定义（抄本文 §二）
5. 周五仪式四问（见步骤 4）
6. 与其它文档的分工表（防重复、防打架，照仓内惯例写）
7. **本机制自身的放弃线**（见步骤 8）

### 步骤 2 · 新建当期作战板（数据，随期替换）
**`.claude/plan/作战板-2026-09.md`**，五段：

| 段 | 内容 | 更新时机 |
|---|---|---|
| **① 本期承诺（基线）** | 这 4 周答应交什么 + 明确不交什么。从冲刺计划的负向清单与 W1–W4 目标搬过来，不重写 | 开期定，期中不改（要改就写一行变更记录） |
| **② 出口门禁** | 搬 [对表冲刺](.claude/plan/对表冲刺-2026-09.md) `W0-E` 那 6 条，每条前加 `[ ]` | 达成即勾 → **这就是当期完成度的分母** |
| **③ 本周任务（≤5 条）** | 每行：`[ ] 描述 — 验收：<一句话可验证事实>` | 周一定，随时勾 |
| **④ 风险与假设登记册** | 从冲刺计划 §风险 8 条迁入做常设；每条带「触发信号 / 应对 / 状态」 | 周五过一遍 |
| **⑤ 偏离记录** | 做了计划外的事就记一行（时间 + 做了什么 + 为什么） | 发生即记 |

> ②③ 的条目**只搬不重写**——冲刺计划仍是「为什么这么排」的真源，作战板只管「做到哪」。

### 步骤 3 · commit 回指约定
**`docs/版本管理规范.md` §2 增补**：commit body 可选尾行 `Refs: R28, W1-3`（需求编号 / 作战板任务号）。

ADR 引用已经做得好（15 篇 ADR / 10 条提交引用），这是把同一习惯推广到需求号与任务号。之后 `git log --grep="Refs: R28"` 能直接答「这条需求花了哪些提交」。

### 步骤 4 · 周五仪式扩为四问（不新增时间，扩现有 15 分钟）
落点是 [复盘-dogfood冲刺-W2-W4.md](docs/planning/复盘-dogfood冲刺-W2-W4.md) 已有的每周小节，**不新建文件**：

1. 跑 `python -m backend.pipeline.usage_report --days 7`，粘表（已有）
2. 摩擦按次数排序 + 结论句（已有）
3. **作战板勾了几条 / 没勾的为什么**（新）
4. **这周做了几件计划外的事 · 元工作是否过半**（新——专治「dogfood 周里 9 个 feat」那种偷跑）

### 步骤 5 · 注意力预算（成本管理的一人项目替代）
**扩 `backend/pipeline/usage_report.py`，不新建工具**——周五只跑一条命令。

新增 `--mix` 段（默认随报表一起打）：读 `git log --since=<窗口> --pretty=%s`，按 Conventional Commits 的 type 分组，打出：

```
工作构成（近 7 天，N 条提交）
  feat 3 | fix 2 | docs 5 | refactor 1 | chore 1
  元工作（docs+chore+refactor+style）占比 58%  ⚠ 超过 50%
```

**只打印警告，不判红**——判红会变成新的假绿动力（宪章禁 `|| true` 是同一条理由）。超了就在周五第 4 问里写一句为什么。

依据是实测：过去 26 天元工作 60%，`docs` 单项 29.5% 已超 `feat` 23.2%。这把[心法 §5](docs/principles/开发心法-多维思维总纲.md) 的主观自检信号变成客观数字。

复用 `usage_report.py` 现有的窗口参数与打印风格；保持它「纯只读、只打印、绝不写 docs 文件」的既有纪律（git log 是只读的）。属双向门，随时可删，**不写 ADR**。

## 七 · 风险

1. **本方案自身就是元工作**（≈3.5 小时、2 个新文档、0 个产品功能），且落在 W1 开工前 2 天。护栏：只新增 2 文件、复用 `usage_report` 不建第二个工具、放弃线与冲刺同日（10-17）受审。**若用户希望，可只做步骤 2+3+7（作战板+Refs+接线，约 1 小时），其余延到 10-17 后。**
2. **作战板可能变成第二张空表**——这是历史已发生两次的失败模式。护栏：勾选是事件驱动（不是每日义务）、日进度走已有的复盘框、放弃线量的是「被更新的天数」而非「填得好不好」。
3. **`--mix` 可能鼓励刷 feat 提交数**来压低元工作占比。缓解：只警告不判红、周五要写原因句；且真正的判决权在自评卡的使用量指标，不在提交构成。
4. **发版 0.11.0 + 打 tag 不可逆**（tag 可删但已推送就尴尬）。护栏：执行前单独确认版本号，且不追溯补旧 tag。
5. **R29 是否该占需求编号**存在争议（PM 机制算不算"需求"）。依据是 R20「项目得有自评/验收的尺子」已开先例；若用户不认，改记进 `requirements/README.md` §5 的 backlog，不占编号。
