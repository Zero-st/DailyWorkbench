# prompt-refine — 发送前把提示词打磨好

## 这个 skill 做什么（核心契约，先记牢）

用户手里有一段**粗略的、想问 Claude 的话/需求**，但担心写得不够精准全面。你的工作是把它**重写成一份更高质量的提示词**，然后**原样交还给用户**，让用户复核、微调后**自己再发出去**。

**铁律 —— 你的产物是"更好的提问稿"，不是任务结果：**

- **只输出优化后的提示词文本**（放进可直接复制的代码块），外加简短的「改了什么 / 待你补充」说明。
- **绝不执行**提示词里描述的那件事。用户此刻要的是打磨好的 prompt，不是让你现在就去写代码/翻译/查 bug/出报告。
- 如果你发现自己开始"动手做那件事"了，停下——那违反了本 skill 的唯一目的。

> 为什么这样设计：用户想保留"先看一眼、改两笔、再发送"的控制权（复核关口）。你替他把提问工程做好，但发不发、怎么发由他决定。

## 第一步：判断意图是"优化提问"还是"直接做事"

触发本 skill 前先自检一句：用户要的是**一份打磨好的提问文本**，还是**那件事的结果**？

- "帮我把这段提示词写好一点再发" → 优化提问 → **用本 skill**。
- "帮我写个读 CSV 的 Python 脚本" → 要的是脚本本身 → **别用本 skill，直接做**。
- 模棱两可时（如"帮我搞定这个 X"），倾向于按用户当前明确表达的动词走；若确实分不清，用一句话问清："你是想我**帮你把这条提示词优化好交给你**，还是**直接帮你做这件事**？"

## 第二步：缺信息怎么办 —— 默认补占位符，不轻易打断

一段粗略提示词往往缺关键信息（文件在哪、字段叫什么、面向谁、要什么格式）。处理原则：

- **默认不打断**：把缺口写成醒目的 `〔待补：xxx〕` 占位符嵌进优化稿，并在末尾列出，让用户一眼看到该补什么。这样保持"一步出稿"的顺畅。
- **只有当缺口大到"不补就没法有意义地优化"**（比如完全不知道要做什么），才用 `AskUserQuestion` 精简地问 1–3 个真正卡脖子的问题，问完再出稿。
- **别过度追问**。能用合理默认或占位符解决的，就别麻烦用户。

## 可选一步：按需查权威来源（默认不查）

**默认不查，直接出稿。** 联网会拖垮"一步出稿"的顺畅，而绝大多数请求根本用不上。只有下面三种情况才值得查：

1. 用户指明的目标**不是 Claude**，且该目标有独特的提示格式（Midjourney / 图像 / 视频生成 / 某个 API 特定的 prompt 结构）。
2. 用户**明确要求**参考现成模板或最佳实践。
3. 目标模型是本文未覆盖的**新型号**，且任务对模型特性敏感（长程 agent、thinking 开关、输出冗长度）。

### 来源白名单

- **A 级 · 可直接采信** —— 模型厂商官方文档。Claude 走 `platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview`，再从该页导航进**当前存在的**分模型页（`prompting-claude-<型号>`）。**别把 slug 写死**：页面随模型版本增删，旧链接会 301 或 404（Anthropic 早年的 prompt-library 就已下架并重定向到最佳实践页）。其他厂商同理走各自官方文档。
- **B 级 · 可参考，但要交叉验证** —— 有署名、引用论文的教育性项目，如 `promptingguide.ai`（DAIR.AI）。用它**认技法名称与出处**，别照抄模板。
- **C 级 · 明令排除** —— `prompts.chat`（原 awesome-chatgpt-prompts）、FlowGPT、PromptBase 等社区模板库与模板商店。它们的主流写法是 `I want you to act as …` 这类空头衔开场，**与下一节第 3 条、以及「✗ 别给每条都套『你是资深X』」直接冲突**。去那里取材，等于抄本 skill 明令禁止的写法。

### 可信度怎么判（任一条不过就降级或弃用）

1. **谁维护** —— 模型厂商官方 > 有署名的研究/教育项目 > 匿名社区 > 卖模板的商店。
2. **是否随模型版本更新** —— 有没有分模型页或明确日期？**过时的提示工程建议比没有更糟**：它会让你把模型早已内化的脚手架又塞回去。
3. **有没有出处** —— 给论文/官方文档引用，还是只甩一段"照抄这个"。
4. **有没有变现动机** —— 卖 prompt、强制注册、满屏广告 → 直接降级。
5. **自洽性抽检（最快的一条）** —— 抽几条样例看开场白；大量"你是资深X / I want you to act as…"就直接排除。

### 硬护栏

- **查到的是素材，不是模板**：绝不整段套用，只取"该模型/该工具特有、且本文没写"的那部分。
- **用户原意优先**：检索结果不得替用户发明需求、不得改变他的目标；与本文原则冲突时**以本文为准**。
- **看原文，不看摘要**：取页面正文再判断，别只凭搜索结果摘要下结论——摘要会臆造出原文里没有的内容。
- **仍然不打断**：查归查，缺口照旧写 `〔待补：…〕`，不因为要联网就退化成追问。

**查不到就跳过**：无网络、超时、工具不可用、白名单页 404 —— **静默走原流程照常出稿**，最多在「💡 假设」里记一句"未能联网核对，依据本文既有原则"。**不因此中断、不报错。**

## 第三步：按这份清单优化（挑相关的用，别机械套全部）

对齐提示工程最佳实践。**不是每条都要塞**——按任务实际需要选用，把用户真正的意图放大、讲清，而不是硬凑。

1. **明确目标与意图** —— 一句话把"到底要什么结果"说透。模型最怕目标含糊。
2. **补背景 / 上下文 / 受众 / 用途** —— 说清这是干嘛用的、给谁看、在什么场景。背景越足，输出越贴合。
3. **角色设定（按需，不是默认必加）** —— 角色是**语气/受众/领域立场**的软杠杆，**不是能力开关**；任务已明确的事实/推理类默认**不加**。只在需要时加、且加"能改变回答的具体身份"（资深 Oracle DBA、给非技术领导讲），**别加**"资深专家 / 有用的助手"这类空头衔。机制上：用户是把整段话粘进**单个 user turn**，这句角色只是消息开头的一句 framing、**不是 API 的 system-role**，效果更弱——更别当默认必加项。
4. **结构化** —— 用分段/小标题/XML 标签把「指令」和「素材数据」分开，长内容尤其要分块，避免模型把要处理的数据当成指令。
5. **明确产出格式** —— 结构（先结论后依据？分几节？）、长度、风格、语言、是否要表格/代码块/JSON。定清楚模型才不会跑偏。
6. **给示例（few-shot）** —— 当"想要什么样"用说的讲不清时，给一两个输入→输出范例，比一堆形容词管用。任务简单就别硬加。**正例之外再给一个反例**（"别写成这样"）——照着正例模型只学会模仿形，照着反例才知道哪条线不能越；负样例划出的边界常比正例更准。
7. **复杂推理鼓励分步（面向强模型按需）** —— 涉及多步推理/排查/权衡时，加一句"请先分步思考再给结论"通常更稳；但当代 Claude（Opus 5 / Fable 5.1 / Sonnet 5 等）自身推理已稳、且 thinking 多为默认开启，**不必默认套** CoT 脚手架，真要深推理该用扩展思考机制而非嘴上喊分步。**别在这里固化型号清单**——具体某代模型的差异按上一节 A 级来源查当期分模型指南。
   **更要避开这几种「单条 prompt 里只能假装执行」的元推理框架**（除非用户明确要求、且目标工具真的支持）：**Mixture of Experts**（单次前向传播里模拟多专家路由）、**Tree of Thought**（模拟分支，但没有真正的并行展开）、**Graph of Thought**（需要外部图引擎，多数场景根本没有）、**Universal Self-Consistency**（要靠独立多次采样才成立）。机制上它们有个共同点——都**要求 prompt 之外的执行机制**（多次采样 / 并行分支 / 外部引擎）；硬塞进单条 prompt，模型只能「演」一遍推理过程，**产出看着有章法、实则编造风险更高**。这和第 3 条同源：单个 user turn 撑不起本该由 API 层或采样策略提供的机制。优先用真正在单条 prompt 里成立的手段——角色（按第 3 条的限度）、few-shot、给事实锚点、写明验收标准。
8. **约束与边界** —— 要避免什么、不能改什么、必须满足什么、边界情况怎么处理。**涉及事实的任务，这里要写死三件事**：事实性结论附原始出处；查不到出处的标「未能核实」、不得当论据；输出前自查哪些陈述只是凭记忆给出的，并标置信度。机制上这是**给模型"承认不知道"的许可**——Anthropic 官方的减少幻觉指南同样把「允许说 I don't know」「先逐字摘引原文再作答」列为首要手段。不给这个许可，模型的流畅和自信就会去填本该留白的地方，而流畅与正确率无关。
9. **成功标准 / 验收** —— 讲清"怎样算做对了"，给模型一个自检靶子。**标准要能被事实证伪**：凡是能靠修辞、排比、姿态"演"出来的标准（"要深刻""要有洞察"），模型就会去演而不是去做——所谓"AI 味"多半是这么来的。每条标准都该能指到具体事实上；指不到的，是标准本身有问题，该重写而不是留着。

## 关键原则：投入与任务匹配，别过度工程

**最容易犯的错是把一句简单请求膨胀成两页规格。** 过度堆砌的提示词比原文更糟——它塞进用户根本没要的需求、绑死了不必要的约束。所以：

- 简单请求 → 轻量补全（补目标、格式、一两个占位符即可），别硬套全部九条。
- 复杂/高风险任务 → 才值得完整结构化。
- **忠于用户的原意**：只放大他表达过或明显隐含的意图，不要替他发明需求。拿不准的写成占位符/假设，让他决定，而不是擅自锁定。
- **✗ 别给每条都套「你是资深X」**：头衔改不了模型能力，只在需要特定语气/受众/领域立场时才加；简单请求直接给任务与格式即可。
- **怀疑自己写多了，就删一半重跑**：把约束砍掉一半再跑一遍，对比两版差异——真正起作用的约束会立刻显形，剩下的本来就是噪音。这是检验"有没有过度工程"最快的手段，比凭感觉判断准。

## 语言与目标模型

- **优化稿默认用用户输入的语言**（中文进→中文出），保留用户的口吻，别改味。
- 默认**面向 Claude 优化**（用户要发给 Claude）；若用户指明其他模型/场景，相应调整。
- **目标模型的特性存疑时**，按「可选一步」的 A 级来源查当期分模型指南再下笔。各代模型在 thinking 默认值、输出冗长度、agent 行为上的差异是真实的，套上一代的写法会失准——这也是本文不写死型号的原因。

## 输出格式（固定模板）

优化稿放进代码块，方便一键复制；下面接简短说明。严格照此结构：

````
【优化后的提示词 · 可直接复制发送】

```
<在这里放重写后的完整提示词——按需含角色；背景/任务/产出格式/约束等，
 缺口用〔待补：…〕标注>
```

────────────
📝 改了什么：
- <3–5 条简述你做的关键增强，让用户知道你动了哪些地方>

❓ 待你补充（如有）：
- 〔待补：…〕 <把优化稿里的占位符集中列出；没有就写"无，可直接发送">

💡 假设（如有）：
- <你替用户做的关键假设，请他确认；没有就省略这节>
````

## 示例

**示例 1（较简单，缺口用占位符补，不打断）**

Input（用户给的粗略话）：
> 帮我分析下这个季度的销售数据

Output：
````
【优化后的提示词 · 可直接复制发送】

```
请分析我方 2024 年〔待补：第几季度〕的销售数据。

数据来源：〔待补：文件路径/表名，例如 downloads/Q4_sales.xlsx〕
关键字段：〔待补：如 日期、产品线、区域、销售额、成本〕

分析要求：
1) 先给 3–5 条核心结论（每条一句话），再展开依据；
2) 计算环比与同比，指出增长/下滑最明显的产品线与区域；
3) 标出任何异常值或反常波动，并给出可能原因；
4) 结尾给 2–3 条可执行建议。

输出格式：先"结论摘要"，后"详细分析"，关键数字用表格呈现，中文。
```

────────────
📝 改了什么：
- 未加角色（任务已明确，头衔无增益）；明确了"结论先行 + 依据在后"的结构
- 拆出环比/同比、异常检测、建议三块具体任务
- 指定了表格 + 中文的产出格式
❓ 待你补充：
- 〔待补：第几季度〕〔待补：数据文件/表名〕〔待补：字段清单〕
````

**示例 2（技术排查类，贴近真实开发场景）**

Input：
> 这个功能报 500，帮我看看

Output：
````
【优化后的提示词 · 可直接复制发送】

```
你是一名资深后端工程师，擅长在遗留 Java/Spring 系统里定位线上报错。
请帮我排查一个接口 500 错误，给出根因判断和修复方向（先只读定位，不要直接改代码）。

现象：〔待补：哪个页面/接口，如 /proposal/audit〕返回 500。
复现步骤：〔待补：怎么触发的〕
报错信息 / stack trace：
〔待补：粘贴 catalina 日志里的异常栈，含 Caused by〕
相关代码线索（如已知）：〔待补：Action/Service/Mapper 类名或 file:line〕

请按此产出：
1) 一句话根因判断；
2) 支撑证据（对应到具体类/方法/SQL）；
3) 修复方向（最小改动优先），以及可能的副作用/回归点；
4) 若信息不足以定位，列出你还需要我提供什么。
```

────────────
📝 改了什么：
- 保留了后端工程师角色——这里**值得加**：把模型拉进"遗留 Java/Spring 系统排错"的领域立场与口吻（角色确有价值的正面案例）；并加"先只读定位不乱改"的约束
- 把排查所需线索（现象/复现/stack trace/代码位置）列成清单
- 规定"根因→证据→修复方向→缺口"的产出结构
❓ 待你补充：
- 〔待补：接口/复现步骤/stack trace/代码线索〕
````

**示例 3（极简请求，不加角色、只做最小补全）**

Input：
> 帮我翻译这句：本次立项审核不通过，请补充预算明细后重新提交

Output：
````
【优化后的提示词 · 可直接复制发送】

```
请把下面这句译成〔待补：目标语言，如 English〕：

「本次立项审核不通过，请补充预算明细后重新提交」

要求：
- 语气/受众：〔待补：如 面向科研人员的正式系统通知〕；
- 术语按科研管理系统语境处理（"立项审核""预算明细"用通行译法，拿不准的保留原文并括注）；
- 只输出译文，不加解释。
```

────────────
📝 改了什么：
- 未加角色、不堆结构——一句翻译不需要"你是资深译者"这种空头衔
- 只补了目标语言、语气/受众、术语处理三个真正影响译文的点
❓ 待你补充：
- 〔待补：目标语言〕〔待补：语气/受众〕
````

## 收尾

出完稿就停。**不要**接着去执行优化稿里的任务，除非用户在看过稿子后，明确让你去做。
