# ADR 格式（本项目版）

**本项目的 ADR 规矩早已定在 [`docs/TECH_CHARTER.md`](../../../docs/TECH_CHARTER.md) 的「附 · ADR 轻量机制」里，本文件不另起一套模板，只做对接说明。** 有分歧以宪章为准。

## 存放与编号

- 位置：`docs/adr/NNNN-<kebab-title>.md`，四位序号，当前已排到 `0012`。
- 编号：扫一遍 `docs/adr/` 取最大号 +1，别跳号、别重号。

## 模板（照宪章原样）

```md
# NNNN 决策标题
- 背景：一句话说清面临什么选择。
- 决策：选 X。
- 理由：因为……（对齐哪条北极星/原则）。
- 代价：放弃了……/ 何时该重估。
```

四行就够。ADR 的价值在于记下*做过这个决定*以及*为什么*，不在于填满章节。

## 可选补充

只在真有价值时加，多数 ADR 不需要：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策被反复重估时有用
- **考虑过的选项**：只在被否掉的备选值得记住时写
- **后果**：只在有不那么显然的下游影响需要点明时写

## 什么时候该写 ADR

宪章的判据是一句话：**只有单向门才写 ADR**（可逆的直接试）。下面三条是这句话的展开版，三条都成立才写：

1. **难以回头**：以后改主意的代价是实实在在的
2. **不看上下文会觉得奇怪**：未来的读者会看着代码纳闷"当初到底为什么这么干？"
3. **是真实取舍的结果**：确实有过别的选项，而你出于具体理由选了这一个

容易回头的决定就别写——反正到时候直接改；不奇怪的决定没人会问为什么；没有真备选的决定，除了"我们做了显而易见的事"之外也没什么可记。

### 哪些够格

- **架构形状。** "我们用单仓(monorepo)。""写模型事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成方式。** "订单和计费之间走领域事件，不走同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都算——只算那些换掉要花一个季度的。
- **边界与范围决定。** "客户数据归客户上下文所有，其他上下文只按 ID 引用。"明确说"不做"和说"做"一样有价值。
- **对显然路径的刻意偏离。** "我们手写 SQL 不用 ORM，因为 X。"任何一个合理的读者会默认相反做法的地方。这类 ADR 能拦住下一个工程师去"修好"一个刻意为之的设计。
- **代码里看不见的约束。** "因为合规要求不能用 AWS。""响应必须在 200ms 内，因为和合作方的 API 契约。"
- **被否掉的备选，当否掉的理由不那么显然时。** 如果你考虑过 GraphQL、出于微妙理由选了 REST，记下来；否则六个月后又有人会提 GraphQL。
