# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一两句话：这个上下文是什么、为什么存在。}

## 语言

**订单（Order）**：
{一两句话描述这个术语}
_避免用_：采购、交易

**发票（Invoice）**：
交付后发给客户的付款请求。
_避免用_：账单、付款申请

**客户（Customer）**：
下订单的个人或组织。
_避免用_：客户端、买家、账户
```

## 规则

- **要有立场。** 同一个概念有多个叫法时，选一个最好的，其余列进 `_避免用_`。
- **定义要紧。** 最多一两句话。定义它*是*什么，不是它*做*什么。
- **只收本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具函数模式）不属于这里，哪怕项目里用得很多。加词之前先问：这是本上下文独有的概念，还是通用编程概念？只有前者才收。
- **自然成簇时用子标题分组。** 如果所有术语都属于同一块紧凑的领域，平铺一个列表就行。

## 单上下文 vs 多上下文

**单上下文（大多数仓库，包括本项目）**：仓库根目录一份 `CONTEXT.md`。

**多上下文**：根目录放一份 `CONTEXT-MAP.md`，列出各上下文、各住哪里、彼此什么关系：

```md
# Context Map

## 上下文

- [订单](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [计费](./src/billing/CONTEXT.md)：生成发票、处理付款
- [履约](./src/fulfillment/CONTEXT.md)：管理仓库拣货和发运

## 关系

- **订单 → 履约**：订单发出 `OrderPlaced` 事件；履约消费它来启动拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费它来生成发票
- **订单 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

技能自行推断该用哪种结构：

- 存在 `CONTEXT-MAP.md` → 读它找各上下文
- 只有根级 `CONTEXT.md` → 单上下文
- 两者都没有 → 第一个术语定型时懒建一份根级 `CONTEXT.md`

多上下文时，推断当前话题归哪个上下文；拿不准就问。
