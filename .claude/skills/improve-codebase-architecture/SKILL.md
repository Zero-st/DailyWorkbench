# Improve Codebase Architecture

把架构上的摩擦点浮出来，并提出**深化机会**：把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

这个命令*以*项目的领域模型*为依据*，并建立在一套共享设计词汇之上：

- 用 Skill 工具调 `codebase-design`，获取架构词汇（**模块(module)**、**接口(interface)**、**深度(depth)**、**接缝(seam)**、**适配器(adapter)**、**杠杆(leverage)**、**局部性(locality)**）及其原则（删除测试、"接口就是测试面"、"一个适配器是假想接缝，两个才是真接缝"）。每条建议都严格用这些词，不要飘成"组件"、"服务"、"API"、"边界"。
- `CONTEXT.md` 里的领域语言给好接缝起名字；`docs/adr/` 里的 ADR 记录着本命令**不该重新翻案**的决定。

## 流程

### 1. 探索

**先定范围再扫：YAGNI。** 深化一个模块之所以划算，是因为它让该模块未来的改动更容易——所以要把额外的权重放在最近改动过的部分。先决定*看哪里*，再去看：

- 用户点了方向（某个模块、某个子系统、某个痛点）→ 直接采纳，跳过下面的推断。
- 否则，回溯一段足够长的提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件和区域——让这些路径先吸引你的注意。如果改动零散、没有明显热点，就把网撒大一点。

先读项目的领域术语表（`CONTEXT.md`）和你要碰的区域相关的 ADR。

然后拉一个 sub-agent 去走代码库。不要套死板的启发式规则；有机地探索，记下你在哪儿感到摩擦：

- 理解一个概念，需要在多少个小模块之间跳来跳去？
- 哪些模块是**浅**的——接口几乎和实现一样复杂？
- 哪里的纯函数只是为了"好测"才被抽出来，而真正的 bug 藏在它们被调用的方式里（没有**局部性**）？
- 哪些紧耦合的模块泄漏过了它们的接缝？
- 代码库的哪些部分没有测试，或者透过现有接口很难测？

对任何你疑心是浅的东西，都做一遍**删除测试**：删掉它，复杂度是收敛了，还是只是挪了个地方？"收敛了"才是你要的信号。

### 2. 用 HTML 报告呈现候选

写一个自包含的 HTML 文件到 **`/home/dev_st/桌面/comtools/tmp/dailyworkbench/`**（本机临时文件的统一落点，不进仓库；目录不存在先 `mkdir -p`，路径含中文要整段加双引号），文件名 `architecture-review-<timestamp>.html`，每次运行都是新文件。用 `xdg-open "<path>"` 给用户打开，并把绝对路径告诉他。

> 之所以不用系统 `$TMPDIR`/`/tmp`：本机全局约定所有临时产物统一进 `comtools/tmp/`，禁止散落到系统临时目录。

报告用 **Tailwind（CDN）** 做布局和样式、用 **Mermaid（CDN）** 画那些"图/流程/时序能可靠传达结构"的图。Mermaid 和手写 CSS/SVG 混用：关系是图状的（调用图、依赖、时序）就用 Mermaid；想要更有编辑感的东西（体量图、剖面图、折叠动画）就手搭 div/SVG。每个候选都要有**前后对比可视化**。要视觉化。

> 提醒：这两个 CDN 需要联网加载。本机断网时图表会渲染不出来，但报告的结构和文字仍可读，不影响拿到分析结论。这份报告是一次性诊断产物、不随 App 分发，所以不受项目"离线优先"北极星约束。

每个候选渲染成一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用大白话描述会改什么
- **收益**：用局部性和杠杆来解释，以及测试会怎么变好
- **前 / 后对比图**：并排、自绘，画出浅在哪、怎么深化
- **推荐强度**：`Strong` / `Worth exploring` / `Speculative` 三选一，渲染成徽章

报告末尾放一节**首选推荐**：你会先动哪个候选、为什么。

**领域用 `CONTEXT.md` 的词，架构用 `codebase-design` 的词。** 如果 `CONTEXT.md` 定义了"日报"，就说"日报入库模块"，不说"FooBarHandler"，也不说"日报服务"。

**ADR 冲突**：如果某个候选和现有 ADR 相悖，只有当摩擦真实到值得重开那份 ADR 时才浮出来。在卡片上明确标注（比如一个警告框：_"与 ADR-0007 相悖，但值得重开，因为……"_）。不要把 ADR 禁止的每一种理论上的重构都列出来。

完整的 HTML 骨架、图形模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

**此时先别提接口方案。** 文件写好之后问用户："这几个里你想探索哪一个？"

### 3. 追问循环

用户选定一个候选后，用 Skill 工具调 `grilling`，和他一起走决策树：约束、依赖、深化后模块的形状、接缝后面放什么、哪些测试能活下来。

决策定型的同时就地产生副作用；用 Skill 工具调 `domain-modeling`，边走边让领域模型保持最新：

- **给深化后的模块起了个 `CONTEXT.md` 里没有的概念名？** 把这个词加进 `CONTEXT.md`。文件不存在就懒建。
- **对话中把一个模糊的词磨精确了？** 当场更新 `CONTEXT.md`。
- **用户以一个有分量的理由否掉了候选？** 提议写 ADR，措辞是：_"要不要我把它记成一份 ADR，免得以后架构复盘再把它提出来？"_ 只在这个理由确实是未来的探索者避免重提所需要的时候才提议；转瞬即逝的理由（"现在不值得"）和不言自明的理由都跳过。
- **想为深化后的模块探索多种备选接口？** 用 Skill 工具调 `codebase-design`，走它的"设计两遍"并行 sub-agent 模式。
