# Codebase Design

设计**深模块（Deep Module）**：一小片接口背后藏着大量行为，架在一个干净的接缝(seam)上，能透过这片接口被测试。凡是在设计或重构代码时，都用这套语言和原则。目标是给调用方杠杆(leverage)、给维护者局部性(locality)、给所有人可测试性。

## 词汇表

严格用这几个词，不要换成"组件(component)"、"服务(service)"、"API"、"边界(boundary)"这类说法——用词一致才是重点。

**模块（Module）**：任何"有接口 + 有实现"的东西。刻意不分尺度——可以是一个函数、一个类、一个包，也可以是横跨几层的一整片切面。_避免用_：单元(unit)、组件、服务。

**接口（Interface）**：调用方要正确使用这个模块所必须知道的一切——不只是类型签名，还包括不变量、调用顺序约束、错误模式、必需配置、性能特征。_避免用_：API、签名(signature)（这两个词太窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部，它的代码本体。区别于**适配器（Adapter）**：同一个东西可以是"小适配器 + 大实现"（比如一个 Postgres 仓储），也可以是"大适配器 + 小实现"（比如一个内存假实现）。谈接缝的时候用"适配器"，其他时候用"实现"。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学一点接口，能撬动多少行为。当一大坨行为藏在一个小接口后面，这个模块就是**深(deep)**的；当接口几乎和实现一样复杂，这个模块就是**浅(shallow)**的。

**接缝（Seam）**_（Michael Feathers 提出）_：一个"不用改动那个位置本身就能改变行为"的地方——也就是模块接口*所在的位置*。接缝放在哪，是独立于"接缝后面放什么"的另一个设计决策。_避免用_：边界(boundary)（这个词已经被 DDD 的限界上下文占用，容易混）。

**适配器（Adapter）**：在某个接缝处满足接口的具体实现物。描述的是*角色*（它填的是哪个槽位），不是*内容*（里面是什么）。

**杠杆（Leverage）**：深度带给调用方的东西。每学一点接口能换来多少能力。一份实现，能在 N 个调用点、M 个测试上收回成本。

**局部性（Locality）**：深度带给维护者的东西。改动、bug、知识、验证都收敛在一处，而不是散落在各个调用方身上。改一处，处处生效。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│     小接口           │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│    深实现            │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块**（要避免）= 大接口 + 少量实现：

```
┌─────────────────────────────────┐
│         大接口                   │  ← 方法多，参数复杂
├─────────────────────────────────┤
│      薄实现                      │  ← 只是层转发
└─────────────────────────────────┘
```

设计接口时问自己：

- 方法数量能不能再少？
- 参数能不能再简单？
- 能不能把更多复杂度藏到里面去？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部完全可以由一堆小的、可 mock、可替换的部件组成，它们只是不属于接口而已。一个模块可以同时有**内部接缝**（只对它自己的实现和测试可见）和**外部接缝**（在它的接口处）。
- **删除测试（The deletion test）。** 想象把这个模块删掉：如果复杂度就此消失，说明它只是层转发；如果复杂度转移到了 N 个调用方身上重新冒出来，说明它真的在挣它的那份价值。
- **接口就是测试面。** 调用方和测试穿过的是同一道接缝。如果你想"越过接口"去测试内部，多半是这个模块的形状不对。
- **一个适配器只是个假想接缝，两个适配器才是真接缝。** 除非确实有东西会随接缝变化，否则不要引入接缝。

## 为可测试性设计

好的接口会让测试变得自然：

1. **接受依赖，不要自己创建依赖。**

   ```javascript
   // 好测：依赖从外面传进来
   function processOrder(order, paymentGateway) {}

   // 难测：依赖是自己 new 出来的
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要制造副作用。**

   ```javascript
   // 好测：纯函数，返回值
   function calculateDiscount(cart) {}

   // 难测：直接改了传入对象的状态
   function applyDiscount(cart) {
     cart.total -= discount;
   }
   ```

3. **接口面小。** 方法越少，要测的东西越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它对调用方和测试展示的那个面）。
- **深度**是**模块**相对它的**接口**衡量出来的属性。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**架在**接缝**上，满足这个**接口**。
- **深度**给调用方带来**杠杆**，给维护者带来**局部性**。

## 被否掉的表述方式

- **把"深度"定义成"实现行数 / 接口行数"的比值**（Ousterhout 原始定义）：这样会鼓励往实现里灌水凑行数。这里改用"深度即杠杆"来定义。
- **把"接口"等同于 TypeScript 的 `interface` 关键字或一个类的公开方法**：太窄了——这里的"接口"包含调用方必须知道的每一件事。
- **"边界(boundary)"**：和 DDD 的限界上下文语义重叠，说**接缝**或**接口**就好。
