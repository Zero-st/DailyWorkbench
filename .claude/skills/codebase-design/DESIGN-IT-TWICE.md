# 设计两遍（Design It Twice）

当用户想为一个选定的深化候选探索多种备选接口时，用这套并行 sub-agent 模式。出处是 Ousterhout 的"Design It Twice"：你的第一个想法很少是最好的那个。

沿用 [SKILL.md](SKILL.md) 里的词汇：**模块(module)**、**接口(interface)**、**接缝(seam)**、**适配器(adapter)**、**杠杆(leverage)**。

## 流程

### 1. 框定问题空间

在拉起 sub-agent 之前，先给用户写一段面向人的问题空间说明：

- 任何新接口都必须满足的约束
- 它会依赖哪些东西，各属于哪一类（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗糙的示意代码，用来把约束落到具体——不是提案，只是让约束看得见摸得着

把这段给用户看，然后**立刻**进入第 2 步。用户读、想的同时，sub-agent 在并行干活。

### 2. 拉起 sub-agent

并行拉起 3 个以上的 sub-agent。每个都必须为深化后的模块产出一个**截然不同**的接口。

给每个 sub-agent 一份独立的技术简报（文件路径、耦合细节、依赖属于 [DEEPENING.md](DEEPENING.md) 里哪一类、接缝后面藏着什么）。这份简报独立于第 1 步给用户看的问题空间说明。给每个 agent 一条不同的设计约束：

- Agent 1："把接口压到最小：目标 1–3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性：支持多种用例和扩展。"
- Agent 3："为最常见的调用方优化：让默认场景一行就搞定。"
- Agent 4（如适用）："围绕端口与适配器来设计跨接缝依赖。"

简报里同时带上 [SKILL.md](SKILL.md) 的架构词汇和 `CONTEXT.md` 的领域词汇，这样每个 sub-agent 起的名字都能跟架构语言和项目领域语言保持一致。

每个 sub-agent 输出：

1. 接口（类型、方法、参数，外加不变量、调用顺序、错误模式）
2. 用法示例，展示调用方怎么用它
3. 实现在接缝后面藏了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 取舍：哪里杠杆高，哪里杠杆薄

### 3. 呈现与对比

逐个呈现各设计，让用户一个一个消化，然后用文字对比它们。从**深度**（接口处的杠杆）、**局部性**（改动收敛在哪）、**接缝位置**三个维度对照。

对比之后给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计里的元素能组合得更好，就提一个混合方案。要有立场：用户要的是一个明确的判断，不是一份菜单。
