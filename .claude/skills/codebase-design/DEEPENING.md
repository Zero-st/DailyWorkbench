# 深化（Deepening）

在给定依赖关系的前提下，怎样安全地把一组浅模块深化成一个深模块。沿用 [SKILL.md](SKILL.md) 里的词汇：**模块(module)**、**接口(interface)**、**接缝(seam)**、**适配器(adapter)**。

## 依赖分类

评估一个深化候选时，先给它的依赖分类。类别决定了深化后的模块要怎样跨过接缝被测试。

### 1. 进程内（In-process）

纯计算、内存状态、没有 I/O。永远可以深化：把这几个模块合并，直接透过新接口测试。不需要适配器。

### 2. 本地可替代（Local-substitutable）

有本地测试替身的依赖（比如用 PGLite 替代 Postgres、用内存文件系统替代真实磁盘）。只要替身存在就可以深化。深化后的模块在测试套件里跑着替身一起测。接缝是内部的，模块的外部接口上不需要暴露端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的、你自己拥有的服务（微服务、内部 API）。在接缝处定义一个**端口(port)**（即接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/队列适配器。

推荐话术的形状：*"在接缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样即便部署上跨了网络，逻辑仍然坐在同一个深模块里。"*

### 4. 真正外部（Mock）

你控制不了的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖当作注入的端口；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器只是假想接缝，两个适配器才是真接缝。** 除非至少能说出两个适配器的必要性（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是多绕了一层。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（只对它自己的实现和测试可见），也有接口处的外部接缝。不要因为测试用到了内部接缝，就把它暴露到接口上。

## 测试策略：替换，不叠加

- 一旦有了针对深化后模块接口的测试，原先那些浅模块上的旧单元测试就成了废物——删掉它们。
- 在深化后模块的接口上写新测试。**接口就是测试面。**
- 测试断言的是透过接口能观察到的结果，不是内部状态。
- 测试应该能挺过内部重构，因为它描述的是行为而不是实现。如果实现一改测试就得跟着改，说明这个测试越过接口测到内部去了。
