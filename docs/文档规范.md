# 文档规范 · 怎么生成一篇文档、怎么命名、放哪里

> 性质：**治理约定 · 规则唯一真源**。与 [版本管理规范](版本管理规范.md)、[开发测试规范](开发测试规范.md)、[TECH_CHARTER](TECH_CHARTER.md) 同级，留 `docs/` 根。
>
> **本文是「规则」的唯一物理副本**——分类树、命名词表、决策表、生成流程只在这里维护。
> [`README.md`](README.md) 只放**索引**（现有文档一览），不再重复规则；`.claude/skills/doc-filing`、仓根 `README.md`、`CLAUDE.md` 只放**指针**。
>
> 机器门禁：`python check_docs.py`（CI 硬门，见 §6）。**改规则 = 改本文；§2 词表改了门禁当场跟着变，不用改脚本。**

---

## 0 · 为什么要有这篇（缘起，非拍脑袋）

2026-09-21 实测：同一套文档规则在仓里有 **3 份副本**，且已经打架——

- `docs/README.md` §1 写「治理**三篇**留根」，`doc-filing/SKILL.md` 写「治理**两篇**」；
- `doc-filing/SKILL.md` 那份「压缩版词表」漏了 `台账`/`演进史`、`心法`/`总纲`、`图解-`、`NNNN-` 四类；
- 仓根 `README.md` §十 的 ADR 枚举停在 0010，磁盘已到 0016；
- 词表写的 `-复盘` 后缀，**实际一篇都没有**——5 篇复盘全是 `复盘-XXX` 前缀形态。

[开发测试规范](开发测试规范.md) §3.0 的判据说得很清楚：**同一个坑复发第 2 次 = 文档失效的实证，必须升级防护等级，禁止再写第 3 份文档。**「活文档漂移」早已达升级线。所以本文不是「第 4 份规范」，而是**把散落的 3 份收敛成 1 份，再给它配一把机器锁**（§6）。

方法论依据：

- **Diátaxis**（[diataxis.fr](https://diataxis.fr/)，Python/Canonical 采用）——借其 *how-to / reference / explanation* 三态。**改编说明**：本仓文档多为**内部决策/过程产物**（路线图、ADR、复盘、选型），Diátaxis 的 tutorial 象限不适用，不硬套。
- **ADR**（[adr.github.io](https://adr.github.io/) / M. Nygard）——决策记录放 `adr/NNNN-<kebab>.md`。
- **Keep a Changelog**（[keepachangelog.com](https://keepachangelog.com/)）——版本变更集中在**仓库根** `CHANGELOG.md`，倒序。
- **Docs-as-code**——规则可解析、可校验、进 CI。

## 1 · 分类树（哪类文档进哪个文件夹）

```
docs/
├─ README.md            文档索引（现有文档一览，只索引不定规则）
├─ 文档规范.md           治理·留根：本文——文档怎么生成 / 怎么命名 / 放哪
├─ TECH_CHARTER.md      治理·留根：技术宪章（北极星 / 选型原则）
├─ 版本管理规范.md        治理·留根：版本 / commit / 「what 与思路落在哪」约定
├─ 开发测试规范.md        治理·留根：最小测试先行、全绿再跑全量
├─ principles/          心法 & 方法论：跨产品/设计/工程的「何时戴哪顶帽子」总纲（宪章之上）
├─ adr/                 决策记录（Architecture Decision Records，单向门才写）
├─ requirements/        需求：用户要什么、需求怎么变的（台账=现状真源，演进史=时间线）
├─ guides/              操作指南（how-to）：一步步「怎么做」的手册
├─ design/              设计 & 评审（explanation）：为什么这么做、代价取舍、方案/评审/原理
│  └─ 功能图解/          单功能三图复盘（架构切片 / 时序 / 业务流程）
├─ planning/            方向 & 进度 & 复盘：路线图、总览、里程碑复盘
├─ research/            选型 & 调研：工具/skill 对比、账本、工具链地图
└─ reference/           参考 & 产物：schema、思维导图、生成的 html（devhtml/）等查阅材料
```

**治理四篇留 `docs/` 根**（`文档规范.md`、`TECH_CHARTER.md`、`版本管理规范.md`、`开发测试规范.md`）：它们是「宪法」级、被全仓广泛引用，单列一层反而增加跳转成本。除这四篇加 `README.md` 外，**`docs/` 根不许再堆平铺文件**。

## 2 · 命名词表（机器可解析 · 唯一副本）

### 文件夹
全小写英文 kebab：`adr guides design planning research reference requirements principles`。（历史目录 `reference/devhtml/`、中文目录 `design/功能图解/` 沿用旧名。）

### 文件
**中文语义名 + 标准词**，词决定去哪个文件夹。**英文名例外**：跨社区标准名保留英文——`TECH_CHARTER` / `README` / `CHANGELOG` / ADR 编号 / `*.sql`。

「位置」列的含义：

| 位置 | 判定方式 | 例 |
|---|---|---|
| `尾` | 文件名（剥掉版本/期次尾巴后）以该词结尾 | `温故复用-设计` |
| `首` | 文件名第一段以该词结尾 | `复盘-MVP闭环首跑`、`项目总览-需求与进度` |
| `整名` | 文件名与该词完全相同 | `README` |
| `正则` | 文件名匹配该正则 | `0016-in-app-progress-view` |
| `豁免` | 该目录（含子目录）下不校验命名 | 生成产物 |

**版本/期次尾巴自动剥离**后再判定：`-v0.8.0`、`-W1`、`-W2-W4`、`-2026-09`、`-2026-09-21`。
例：`工作台走查评审-v0.8.0` → 剥成 `工作台走查评审` → 命中尾词 `评审`。

## 3 · 「新文档去哪」决策表

1. 是**单向门决策**（不可逆、要留证）？→ `adr/NNNN-<kebab>.md`，3 行：决策 / 理由 / 代价。
2. 是**「用户要什么 / 这需求怎么变的」**？→ `requirements/`（现状改 `需求台账.md` 一行，过程追加 `需求演进史.md` 一条）。
3. 是**实施计划 / 待办规划**（「接下来怎么改代码」）？→ **不进 `docs/`**，放 `.claude/plan/<task>.md`（英文 kebab，见用户全局约定）。
4. 是**版本变更记录**？→ 仓库根 `CHANGELOG.md`，不新开文件。
5. 否则按 **§2 词表**落对应子目录：讲「怎么做」→`guides/`；讲「为什么 / 怎么设计 / 什么原理」→`design/`；「选型/调研」→`research/`；「方向/进度/复盘」→`planning/`；「schema/思维导图/生成产物」→`reference/`；**跨产品/设计/工程的方法论·心法（何时戴哪顶帽子）**→`principles/`。
6. 拿不准 → 先看现有同类落在哪个目录，就近归位；仍不确定就默认 `design/`（解释类），事后可迁（双向门）。

**分工边界**：`docs/` = 沉淀下来的**项目知识**；`.claude/plan/` = 过程性的**实施计划**；仓根 `README.md`/`CHANGELOG.md` = 社区标准位置。三者不混。

> **当期作战板**（`.claude/plan/作战板-<期>.md`）按这条边界归 `.claude/plan/`——它是高频改动的过程件，不进 `docs/`。它的**规则**才是沉淀知识，在 [`guides/项目管理-操作指南.md`](guides/项目管理-操作指南.md)。与「自评指南 ↔ 自评卡」是同一种分工。

## 4 · 文档生成流程（从「想写」到「可维护」）

### 4.0 · 第零问：这篇该不该存在？

**默认答案是「不该」。** 文档是有维护成本的负债，每多一篇就多一处会漂移的地方（§0 就是代价的实证）。开写前先过三问：

1. **已有文档能不能加一节？** 能就加，别新开。
2. **这是知识还是过程？** 过程件（这次怎么改代码）→ `.claude/plan/`，不进 `docs/`。
3. **半年后还有人读吗？** 一次性的中间产物，聊完就丢，别落盘。

只有三问都过，才走下面的流程。

### 4.1 · 五步

| 步 | 动作 | 产出 / 门禁 |
|---|---|---|
| ① **定性质** | 照 §3 决策表判品类 | 知道进哪个目录 |
| ② **定名字** | 照 §2 词表选词 + 中文语义名 | 文件名；`check_docs.py` C2 会查 |
| ③ **先画图**（非免图档） | 照 [`guides/业务功能开工-图先行指南.md`](guides/业务功能开工-图先行指南.md) 按不确定性分档：思维导图捋业务 → 流程/时序图定思路 | 图（可抛）；软自检，小改免图 |
| ④ **写正文** | 套 §4.2 骨架 | 文档本体 |
| ⑤ **登记** | 补 [`README.md`](README.md) 索引一行（**一句话，≤200 字符**）；被引用的确认相对链接可解析 | `check_docs.py` C1/C4 会查 |

**需求类另加**：非免图档要在 `requirements/需求台账.md` 改一行现状、`requirements/需求演进史.md` 追加一条过程（CLAUDE.md 第 4 条）。
**收尾对接**：功能做完走 [`guides/功能图解复盘-指南.md`](guides/功能图解复盘-指南.md)，三图落 `design/功能图解/图解-<模块>.md`。

### 4.2 · 骨架（所有品类通用的头）

```markdown
# <标题>

> 性质：<治理约定 / 设计说明 / 操作指南 / 调研账本 / 里程碑复盘 …>。
> 上位：<它从属于哪篇>；关联：<姊妹篇>。
> <这篇回答什么问题，一句话。>

---

## 1 · <第一章>
...

---

## N · 变更记录
| 日期 | 改了什么 | 为什么 |
```

各品类的额外要求：

- **ADR**：只要 3 行——**决策 / 理由 / 代价**。写长了说明它不是 ADR，是设计文档，该进 `design/`。
- **复盘**：必须有「预期 vs 实际」的对表，没有对表的不叫复盘，叫流水账。
- **指南**：必须有**可粘贴的命令**，不能只写「记得检查 X」（照 [开发测试规范](开发测试规范.md) §3.0「查不干净就退一步」）。
- **调研/选型**：必须标**来源等级**与**采纳/不采纳及理由**，不采纳的也要留。

### 4.3 · 写作红线

- **只写能被证伪的话**。「性能不错」→「本机 1000 条 1.2s」。
- **数字断言要标日期**，否则半年后没人知道它过期没有。
- **外部数据必须过渲染层**，别把 markdown 语法/emoji 直接抄进表格（[界面设计准则](design/界面设计准则.md) §4，这坑复发过 4 次）。
- **不复制规则**。要引用别处的规矩，写**指针**（「见 X §Y」），不抄正文——抄一次就多一份会漂移的副本，这正是 §0 的病根。

### 4.4 · 退役

文档不再成立时（功能删了、方案换了）：**改或删，不要留着**。

- 部分过期 → 就地改，并在「变更记录」记一行。
- 整篇作废但有史料价值 → 在开头加一行 `> ⚠️ 已作废（YYYY-MM-DD）：<被谁取代>`，保留文件。
- 纯噪音 → 删文件 + 删 `README.md` 索引行。

**删文件必须同步删索引行**，否则 `check_docs.py` C1 会报死链（这正是它存在的意义）。

## 5 · 谁是真源（别处只许放指针）

| 位置 | 该放什么 | 不许放 |
|---|---|---|
| **本文** | 分类树 / 词表 / 决策表 / 生成流程 —— **规则的唯一副本** | — |
| [`README.md`](README.md) | 现有文档索引（一篇一行，一句话） | 规则正文 |
| `.claude/skills/doc-filing/SKILL.md` | 「开工先读本文」的强制入口 + 三步流程 | 词表副本 |
| 仓根 `README.md` | 指向本文的一句话 + 最常翻的几篇 | 分类规则、ADR 全量枚举 |
| `CLAUDE.md` | 一行指针 | 规则正文 |

**改了归属或命名规则 → 先改本文**，别处只跟着改指针。

## 6 · 机器门禁：`check_docs.py`

```bash
python check_docs.py           # 报告模式：打印现状，恒退 0
python check_docs.py --check   # CI 硬门：任一项违规退出 1
```

四项检查：

| 项 | 查什么 | 拦住的真实事故 |
|---|---|---|
| **C1 索引一致性** | `docs/` 下每篇 `.md` 都在 `README.md` 索引里有一行；索引里的链接都能解析 | 漏收（实测 1 篇）、删文件留死链 |
| **C2 命名词表符合** | 每篇的「目录 ↔ §2 词表」匹配；**词表从 §2 表格解析，不在脚本里留副本** | 野文件乱放（`随手记.md` 扔进 `design/` 会红） |
| **C3 副本冲突** | `doc-filing/SKILL.md` 与仓根 `README.md` 里若长回规则正文即红 | §0 那三份副本复发 |
| **C4 索引行长上限** | 索引单行 ≤ 200 字符 | 把正文摘要抄进索引（实测最长一行 822 字符，是 16 条 ADR 摘要的第二份副本） |

**fail closed**：词表解析不出来（哨兵丢了、格式坏了、行数异常少）时门禁**直接红**，绝不「解析为空 → 无规则 → 全绿」。这条有 pytest 专门守着。

**反向判据**（照 [开发测试规范](开发测试规范.md) §3.0 防门禁通胀）：**拦不住任何真实事故的检查项是废话，该删。**

### 6.1 · 门禁拦不住的那半（人工复核，半年一次 / 改规则后）

C3 只认「词表词 + 目录名同现」这一种副本形态；有人用大白话重写规则它抓不到。索引行里的**数字断言**（如「R01–R28」）过期了它也不知道。可粘贴命令：

```bash
# 这两个文件是否偷偷长回了规则正文（应只剩指针）
grep -nE '指南|设计|评审|选型|复盘|路线图|台账' README.md .claude/skills/doc-filing/SKILL.md \
  | grep -vE '\.(md|sql|html)'

# 仓根 README 的 ADR 枚举是否落后于实际（应只剩目录指针，无枚举）
ls docs/adr/*.md | wc -l ; grep -o '0[0-9][0-9][0-9]' README.md | sort -u | tail -1

# 索引里的需求编号是否与台账对得上
grep -n '需求台账' docs/README.md ; tail -3 docs/requirements/需求台账.md
```
