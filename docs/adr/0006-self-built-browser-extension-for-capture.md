# 0006 · 捕获层自研浏览器扩展（而非 Obsidian Web Clipper / 书签小工具）

- 状态：**已接受**
- 日期：2026-09-03
- 关联：[捕获收件箱-浏览器扩展-设计](../design/捕获收件箱-浏览器扩展-设计.md)、[0001 零构建北极星](0001-zero-build-north-star.md)、[0005 PC-first](0005-pc-first-drop-native-mobile.md)、[知识飞轮-路线图](../planning/知识飞轮-路线图.md)

## 背景

飞轮捕获环需要「读帖当场选中一段 + 写下感悟 → 落进收件箱」。已有的收件箱视图要求离开帖子、切标签、手动粘链接，摩擦仍在。三条候选路：

- **A · Obsidian 官方 Web Clipper**：装官方扩展 + 配模板，直接写 vault `收件箱/`。
- **B · 书签小工具（bookmarklet）**：选中 → 点书签 → 切到工作台并用 URL 参数预填 → 写感悟。约 30 行，零安装。
- **C · 自研 Chrome MV3 扩展**：页内浮按钮/右键 → shadow DOM 面板写感悟 → background fetch 直连后端。

## 决策

**选 C，自研 MV3 扩展**，并要求它「零站点解析」（不写任何平台专属 DOM 选择器，只用 `getSelection()` / `og:*` / `document.title`）。

## 理由

- **唯一能做到"不离开帖子页"**。A 保存时 Obsidian 窗口会弹到前台，实际比切浏览器标签**更打断**；B 必然切标签。捕获摩擦是本环节的第一约束，页内完成是唯一满足它的形态。
- **A 在本机有额外风险**：依赖 Obsidian 桌面端常开，且 `obsidian://` 协议在 Linux（AppImage 常见）未必注册成功，需先验证；A 也不写 `_index.jsonl`，工作台侧还得改成扫文件夹读，反而多一套读路径。
- **数据落点更合适**。A 直接写 vault，而沉淀根当前 = `devmd` 库根，个人感悟无条件进公开库不妥；C 落仓根 `inbox.local.json`（gitignore），收件箱作为"暂存工作集"语义更正确，状态变更（待处理/已蒸馏/已归档）也不必去改 frontmatter。
- **零站点解析把维护面压住**。扩展最大的长期成本是站点改版，而本设计对站点 DOM **零依赖**；平台识别复用工作台已有 `detectPlatform(url)`，Python 侧不复制域名表，无双份真源。

## 代价（明确承担）

- **多一个要维护的构件**（`extension/`），需开发者模式 load unpacked；Chrome 未来 MV3 政策变化需跟随。
- **新增后端写端点**（`/api/inbox/*`）与一个持久化文件，比"纯 localStorage"多一层；因此必须配 Origin 允许列表，否则任意网页可写本地 API。
- **不是"零构建"的反例但接近边界**：扩展本身无需构建（纯 JS/HTML，无打包），故仍守 0001 北极星；若将来需要打包工具链，须回到本 ADR 重估。
- 放弃了 A 的"多段高亮/按站点模板"现成能力。若后续确实需要，可叠加 A 作为可选增强（两者数据最终都汇到收件箱/蒸馏库，不冲突）。

## 何时重估

- Chrome 收紧 MV3 或 load unpacked 策略，使自维护扩展成本显著上升。
- 出现"多段高亮 + 全文剪藏"的强需求，超出零站点解析能覆盖的范围。
- 捕获重心从 PC 移到手机（届时走路线图 Phase 3 云收件箱，另写 ADR）。
