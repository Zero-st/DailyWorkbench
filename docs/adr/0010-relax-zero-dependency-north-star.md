# 0010 松绑「零依赖」北极星为「依赖极简且可撤回」（修订 0001）

- 背景：[0001](0001-zero-build-north-star.md) 把「零构建·零依赖·离线可跑」定为北极星，但实践暴露两个问题：① 「零依赖」把三扇**可逆性截然不同**的门捆成一扇——「引钉版库」随时能撕掉换回手搓（双向门），「引构建 step」视图重写成组件就回不去（单向门），二者代价差一个数量级却被一视同仁地卡死；② 「离线可跑/双击 index.html」已**名存实亡**——`app.js` 是 ESM，浏览器对 `file://` 下 ESM+SW 普遍受限，真实交付形态早已是 `python -m backend.server` 起本地 http。代价是前后端手搓了大量**真·知识重复**的轮子（日期格式化散落 5+ 处、YAML frontmatter 解析 4 份独立实现），维护累。
- 决策：北极星修订为 **「零构建 · 依赖极简且可撤回 · 本地起服务即可跑（离线优先）」**。据此：
  - **T1（采纳）**：允许引入**钉版、可撤回**的第三方库——前端沿用 `vendor/` 钉版模式（`marked.min.js` 是先例），后端允许一个根级可选 `requirements.txt`。降为**双向门，不必写 ADR，直接试**。
  - **T3（采纳）**：正式承认「双击 index.html」不再是保证路径，真实入口是本地起服务；止住这处文档漂移。
  - **T2（本次不做）**：引入**构建步骤**（打包/编译/JSX 模板/全量 TS）仍是**单向门**，需另写 ADR。触发条件：视图层字符串拼接（`info.js` 68 处 innerHTML 拼接）或前端类型盲区成为**主要**痛点时再评估。
- 理由：对齐单向门/双向门原则——钉版库可逆故可直接试，构建 step 近乎不可逆故仍设闸（design-principles 卡 5）；不提前上构建是 YAGNI（卡 4，T1 已能解掉当前绝大部分「累」）；只换真·知识重复的件，SSE/`net.js`/`state.js` 这类刻意且极小的手搓保留、不为库而库（卡 11）。
- 代价 / 何时重估：
  - 放弃了「三年后绝不会因第三方腐烂而跑不起来」的最强保证；护栏补偿——**版本必须钉死**、**App 核心链路缺依赖时不许直接崩**（照抄现有 mcp/opencli 的优雅劣化范式）、**第三方封装在 adapter 层**（前端 `js/core/`、后端 `backend/utils/`）不让类型渗进各视图，保住「可随时撤回」。
  - 何时升 T2 并回写单向门 ADR：视图层拼接/类型盲区成为主要痛点，或出现第二人长期维护时。
