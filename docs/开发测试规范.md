# 开发测试规范 · 最小测试先行，全绿再跑全量

> 治理约定，与 [版本管理规范](版本管理规范.md)、[TECH_CHARTER](TECH_CHARTER.md) 同级。核心一句：**每个模块/接口先用最小测试验通，所有子路径都绿了，才跑一次整份数据/全量流程——避免反复全量，省 token、省成本、省时间。**
>
> 本文档管小改动这一档；新模块/新 seam/新外部依赖/多分支逻辑这类复杂改动，走 `tdd` skill 的红绿循环（`.claude/skills/tdd/SKILL.md`），别在这两处重复写判断标准。

## 1 · 为什么（第一性）

全量跑（全量 LLM 调用 / 全量抓取 / 全量重建）既慢又费钱，且一旦中途某个模块有坑，前面烧的 token 全白费、还要重来。**把验证左移到最小单元**：用一次调用、一条合成数据、一段纯逻辑就能证伪的，绝不用整份数据去证。最小测试是"不对称投资"——极小成本换取"这条线路到底通不通"的确定性。

## 2 · 规范（怎么做）

开发一个功能/接口/管线时，按下面顺序推进，**上一档不绿不进下一档**：

1. **静态门**（零成本）：语法/编译先过——后端 `py_compile`，前端 ES Module 语法门（`node` 动态 `import()` 只判 `SyntaxError`，`node --check` 对 ESM 有假阴性）；改了 `css/js/index.html` 跑 `bump_version.py`、`check_design_tokens.py`。
2. **纯逻辑单测**（零网络）：能用合成输入跑的分支逻辑（幂等标记、去重、边界、异常兜底），就地写个 inline 断言验，别拉真服务。
3. **单点接口最小测试**（一次调用）：外部依赖（LLM/向量库/HTTP 端点）先打**一条**——探维度、embed 一句、upsert 一行、curl 一个坏参数看是否优雅降级。**先证"通路 + 契约 + 降级"，再谈规模。**
4. **单模块小样**（≤ 一个批次）：管线里一步先跑 3~5 条，核对产出字段/缓存/幂等（二次跑应命中缓存、不重复烧）。
5. **全绿后，唯一一次全量**：以上都绿，才清标记/跑整份数据。全量前想清楚"这次全量到底为验证什么"，且尽量复用缓存（如只补向量、不重烧摘要）。

配套原则：
- **结合已知坑点**：验证清单里显式覆盖踩过的坑（见 §3），别只测 happy path。
- **可降级不阻断**：外部依赖缺失/失败，模块要优雅跳过、保留旧数据、跨轮自愈（缓存标记），而不是崩或静默丢结果。
- **成本护栏**：全量要有上限（每轮条数上限、缓存幂等），失败落盘可审、不无界重试。

## 3 · 已知坑点台账（验证时逐条对照）

### 3.0 · 升级判据 —— 为什么这是「台账」不是「清单」

> **同一个坑复发第 2 次 = 文档失效的实证，必须升级防护等级，禁止再写第 3 份文档。**

**缘起（一条被实证的教训）**：「emoji 渲染成豆腐块 ☒」2026-08-31 立了硬性红线（[界面设计准则](design/界面设计准则.md) §4），规则同时写进 **5 个文档**——之后仍复发 **3 次**（09-02 v0.9.1 批量迁移、09-20 D3 主按钮、09-21 进度视图状态列）。

[TECH_CHARTER](TECH_CHARTER.md) 维度三早就写下了答案：**「准则说的规矩必须有脚本查，否则和任何文档一样漂移」**——`check_design_tokens.py` 正是这么诞生的。缺的从来不是哲学，是**触发条件**。本节就是那个条件。

**三档防护**（与[心法](principles/开发心法-多维思维总纲.md) §4「绝不跳档」同一逻辑，只是对象从「功能」换成「防护」）：

| 档 | 形态 | 何时必须升到下一档 |
|---|---|---|
| **文档** 📄 | 写进准则/规范，靠人记 | 第 1 次踩坑的默认档。**复发第 2 次即判定失效** |
| **门禁** 🤖 | 机器查，CI 会红 | 复发第 2 次必须到这档。**查不干净就退一步**：把人工步骤写成**可粘贴的命令**，而不是一句「记得检查」 |
| **设计** 🏗 | 结构上不可能犯（接口上就没有那个危险操作） | 上了门禁还犯 |

**反向判据**（防门禁通胀，照宪章「回溯校验」）：**拦不住任何真实事故的门禁是废话，该删。**

**怎么用**：踩坑当天在 §3.1 加一行或把复发次数 +1；到 2 次就**当场**升级，别等复盘。

### 3.2 · 取数 / 管线坑点（属 📄 档，验证时逐条对照）

来自本仓资讯语义检索（Zilliz + BYO embedding）实战，跨功能通用：

- **外部模型/端点先探通再规模化**：厂商 base 路径/模型 id/权限极易错（如火山方舟 **Coding Plan** 是 `/api/coding/v3` 且 chat=`glm-5.3`、embedding=`doubao-embedding-vision`(2048维)，普通 `/api/v3` + 通用模型名 404）。**先 1 条 embed/chat 打通，别直接全量。**
- **向量库 schema 用最小 schema 先建通**：Zilliz/Milvus REST v2 字段参数键是 `elementTypeParams`（非 `params`）；serverless DDL 慢（超时放宽到 90s）。**先建 id+vector 最小表验通，再补标量字段。**
- **大响应易 `IncompleteRead`**：高维向量 × 大批次（2048×10）响应体大、跨区连接易截断；靠"重试 + 缓存 e 标记跨轮自愈"，必要时**调小 embedding 批次**（响应减半）。
- **带密钥请求不得降级不校验 TLS**：抓公开内容可降级，但带 `Authorization` 的请求降级 = 泄 key，只在校验 ctx 下重试。
- **入参健壮**：接口对坏参数（非数字 topk 等）要兜底默认、返回 200/降级，而非抛异常落 500。
- **幂等标记只标真正成功项**：批处理里被跳过的项不能连带标记"已完成"，否则永久遗漏且不重试。

## 4 · 反例（别这么干）

- 上来就点"同步/全量"，管线中段某步坑了，整轮 token 白烧。
- 只在真全量里才发现"模型名错/字段键错/降级泄密钥"这类一条调用就能暴露的问题。
- happy-path 过了就宣布完成，不覆盖失败/边界/降级路径。
