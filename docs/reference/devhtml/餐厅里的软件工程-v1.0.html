餐厅里的软件工程

软件看不见摸不着，但它和一家餐厅惊人地像：有顾客看得见的前厅，有看不见的后厨和仓库，也要经历选址、装修、试菜、开业、天天经营。这一页用「开一家餐厅」这件事，把软件的三个问题讲清楚：怎么想、长什么样、怎么做出来。

开场

软件是一家你看不见的店

先看一件你每周都做的事：点外卖。手指戳几下，三十分钟后饭到门口。这中间到底发生了什么？

你手机上的 App 是前厅，你只看到菜单和按钮。你的订单被送进某台远处电脑里的后厨，它算钱、派单、通知商家。你的地址、历史订单、余额，都躺在仓库里。而付款、发验证码短信、地图导航，则是店家花钱找的供应商。

所以「软件」不是一个东西，是一整家店。「做软件」也远不止「敲代码」三个字，它是开一家店的全流程：想清楚开给谁，画图纸，装修试做，试菜，试营业，开业，然后天天经营、不断换菜单。

前厅
你手机上看到的菜单、按钮、动画
后厨
远处那台电脑：算钱、派单、发通知
仓库
你的地址、历史订单、余额存放处
供应商
支付、短信验证码、地图，都是外接的

第一道 · 怎么想

软件开发思维

程序员并不比别人聪明，只是养成了一套面对复杂事情的固定习惯。这 8 个习惯，每一个你都在厨房和饭桌上用过。

拆解

decomposition
生活里

年夜饭要做十二道菜，没人会直接「开始做年夜饭」。你会先列菜单，再按凉菜、热菜、汤分工，每道菜再拆成买、洗、切、炒。

软件里

「做一个外卖 App」这句话没法直接干。先拆成登录、看菜单、下单、支付、配送跟踪五块，每块再拆到一个人几天能做完的小任务。程序员把拆出来的每一块叫模块 module。

常见翻车

不拆就开工。做到一半发现哪都连着哪，改一处坏三处。

抽象

abstraction
生活里

世界上有几万道菜，但每道菜都是「食材、加工、装盘」。厨师学的不是几万套孤立步骤，是这个通用框子，再往里填不同的料。

软件里

程序员把反复出现的做法提炼成一个可以反复调用的「模子」，叫函数 function。写一次「算折扣」，全店所有地方都用它；改价格规则时只改这一处。

常见翻车

同一段逻辑复制粘贴到十个地方。有一天要改，漏改了三处，谁也不知道。

流程即算法

algorithm
生活里

菜谱就是算法。「水开后下面」是条件，「翻炒直到金黄」是循环，「最后撒葱花」是顺序。写到什么程度算清楚？到一个从没做过这道菜的人照着也能做出来。

软件里

电脑比最笨的新手还笨，一步都不能省。程序就是写给电脑的菜谱，只用三种结构就能描述一切：顺序做、按条件选、重复做。这套写清楚的步骤叫算法 algorithm。

常见翻车

默认电脑「应该懂」。它不懂。「稍微炒一下」这种指令，电脑会当场罢工。

边界与意外

edge case / error handling
生活里

好餐厅不只会做菜，还提前想好了：客人点了菜单上没有的菜怎么办？盐用完了怎么办？二十桌同时进门怎么办？这些不是主流程，却决定了店垮不垮。

软件里

顺利的那条路通常只占代码的三成，剩下七成在处理「用户没填手机号、网络断了、余额不够、同一秒一万人抢券」。这些奇怪情况叫边界情况 edge case，处理它们叫异常处理 error handling。

常见翻车

只演示「一切顺利」的路径。上线第一天，被用户多打的一个空格打垮。

权衡

trade-off
生活里

装修一家店，快、好、省三样最多选两样。开业只剩两周？那就先把厨房弄好，墙纸以后再换。你心里清楚这是欠了一笔账。

软件里

任何方案都有代价：功能多就慢，安全严就麻烦，做得快就欠账。好程序员不问「哪个最好」，而问「这个阶段什么最重要，我们愿意在哪儿吃亏」。为了赶进度先凑合、以后要还的那笔账，有专门的名字：技术债 technical debt。

常见翻车

追求一次做到完美。两年后店还没开，隔壁已经换了三轮菜单。

复用

reuse
生活里

连锁店不会每家自己磨豆腐，中央厨房统一送半成品。灶台、冰箱直接买成品，没人自己焊。

软件里

登录、支付、发短信、画图表，全世界早有人做好了现成的，叫库 library。连整套「后厨怎么布局」都有标准模板，叫框架 framework。程序员大部分工作是选对、装好、接上，而不是从零发明。

常见翻车

什么都自己写。自己写的登录系统，漏洞比现成的多十倍。

迭代

iteration
生活里

聪明的老板先开一个小店，甚至先摆一周摊，看看有没有人买，再决定要不要租大铺面。

软件里

先做一个只有核心功能、能跑通的最小版本，叫 MVP minimum viable product，拿给真实用户用，根据反馈一版一版加。所以你手机里的 App 总在更新：v1.0、v1.1、v2.0，每个数字都是一次「换菜单」。

常见翻车

憋一年做「完整版」。上线才发现，用户根本不想要这个。

站在顾客那边

user-centered
生活里

顾客不关心你后厨用的是德国灶还是日本刀，只关心好吃、上菜快、别拉肚子。

软件里

用户不关心你用什么语言、什么架构，只关心能不能三步内做完想做的事、会不会卡、数据会不会丢。所有技术选择最后都要翻译回一句话：用户体验到了什么不同？这叫用户体验 UX, user experience。

常见翻车

技术上很炫的功能，用户找不到入口。

一个人做项目，要轮流戴四顶帽子

上面 8 条是「厨师」的脑子。但一家店要开好，至少四种人的脑子都得有。人少的时候，就一个人轮着戴。

店长帽产品 · product

这道菜有人点吗？为谁做？先问值不值得做，再问怎么做。

装修师帽设计 · design

陌生人进门第一眼，会不会觉得这家店「坏了」？功能全对但看着乱，第一印象就没了。

厨师长帽工程 · engineering

三年后换一批厨师、换个铺面，这套流程还跑得起来吗？

老板帽决策 · decision

这扇门走错了，能退回来吗？可逆的事快点试，不可逆的事写下来再定。

顺序很重要：先戴店长帽判断值不值得，再戴另外三顶。最常见的病是「厨师帽太舒服」，一直在后厨打磨刀工，回避「这道菜到底有没有人吃」这个难受的问题。

为什么要分成这么多间屋子

你可能会想：全塞一间屋不行吗？路边摊可以。但店一大，分屋子的好处就出来了：

  • 换菜单不用拆厨房。改界面不必碰后端，后端换更快的做法，前厅一行不动。程序员叫这解耦 decoupling，意思是「彼此不粘着」。
  • 各干各的。前厅的人不用会炒菜，厨师不用会招呼客人。软件团队也照这个分：前端、后端、数据库、运维，各有专精。
  • 出事好查。菜咸了查后厨，上菜慢查服务员，账对不上查仓库。屋子分得清，故障就能圈得小。

这种一层一层的划分叫分层架构 layered architecture。「架构」这个词听着高深，其实就是「屋子怎么划分、门开在哪」的那张平面图。

小卖部，还是连锁商场

屋子怎么分，还有一个更大的选择：所有屋子放在一栋楼里，还是拆成几十家独立门店？这是软件行业争论最多的问题之一。

小卖部 单体 · monolith连锁商场 微服务 · microservices
像什么一间屋子，收银、货架、仓库全在一起，一个老板全管。几十个独立门店，各有各的后厨和仓库，靠统一的点菜单格式协作。
好处简单、开得快、一个人看得懂、出事一眼找到。一家店着火不影响别家。每家店可以独立换菜单、独立扩张。
代价店一大就挤：几十个人同时装修一间屋会互相绊脚。管理成本剧增。店与店之间传话可能丢、慢、乱，还得养一整套「商场物业」。
适合谁绝大多数新项目和小团队。团队上百人、用户上亿、小卖部已经真的撑不住的时候。
最常见的错误，是刚起步就学大公司拆几十家「门店」，结果一个人管一座空商场。先做小卖部，撑不住了再拆。这本身就是第一道里说的「权衡」。

代码本身放在哪里

屋子说的是运行中的软件。那程序员写的那些「菜谱」本身怎么管？也有一套对应。

菜谱本代码仓库 · repository

所有菜谱装订成一本，放在一个地方，谁都从这本抄，不许各存各的版本。

章节模块 / 目录 · module

凉菜一章、热菜一章、汤一章。对应代码里一个个文件夹，找东西按章翻。

修改记录版本管理 · Git

每次改菜谱都盖章记下「谁、何时、改了哪一行、为什么」，随时能翻回上一版。几个厨师同时改也不会互相覆盖。

试做间开发 / 测试 / 生产环境 · environments

新菜先在试做间做，再到试菜间请内部人尝，最后才上正式菜单。三个地方分开，绝不在营业中的灶台上试新菜。

第三道 · 怎么做出来

软件开发全流程

从「我想开家店」到「顾客天天来」，餐厅要走七站。软件一模一样，行业里叫它软件开发生命周期 SDLC。每一站看四件事：餐厅里做什么、软件里做什么、留下什么东西、最常在哪翻车。

  1. 1
    想清楚开什么店→

    需求分析

    requirements
    餐厅里

    开给谁吃？写字楼白领的快餐，还是家庭聚餐？人均多少钱？周边有几家竞品？这些不问清就装修，是最贵的错误。

    软件里

    跟用户和老板反复聊：「你说的『像美团』，具体要它哪三个功能？谁用？多久用一次？」把模糊的愿望翻译成一条条能验收的句子。

    留下什么

    需求文档 PRD、用户故事（「作为骑手，我想一眼看到最近的三单，以便……」）、优先级清单。

    最常翻车

    老板一句「做个像美团的」就开工。需求阶段一句没问清的话，到上线时要用一百行代码和三次返工来还。

  2. 2
    画图纸→

    设计

    design
    餐厅里

    菜单长什么样、桌子怎么摆、顾客从进门到落座走哪条线、后厨灶台和冰箱怎么放才不撞人。

    软件里

    分两层。界面设计：页面长什么样、按钮放哪、点了跳哪。技术设计：分几间屋子（架构）、仓库里放哪些格子（数据库设计）、服务员用什么单子（接口设计）。

    留下什么

    原型图 prototype、高保真设计稿、架构图、数据库表结构、接口文档。

    最常翻车

    跳过设计直接开工。等于不画图纸就装修，做完发现冰箱门打不开。

  3. 3
    装修、备料、试做→

    开发编码

    development
    餐厅里

    按图纸装修、买设备、招厨师、把每道菜一道道试做出来。工期最长、最忙的一段。

    软件里

    程序员按设计稿把前厅（前端）、后厨（后端）、仓库（数据库）一块块写出来、接起来。每做完一块，同事互相看一遍，叫代码评审 code review，像老师傅尝一口徒弟的菜。

    留下什么

    能运行的代码，提交进代码仓库。每一次改动都有记录、有说明。

    最常翻车

    外行以为这一步就是全部（「程序员不就是写代码吗」）。它通常只占总时间的三到四成。

  4. 4
    试菜、模拟高峰→

    测试

    testing
    餐厅里

    每道菜自己先尝咸淡；整套菜配着上一遍，看前菜和主菜打不打架；请一屋子朋友来模拟饭点高峰，看后厨顶不顶得住。

    软件里

    对应三层：单元测试一道菜一道菜尝；集成测试几道菜一起上；端到端测试完整模拟一个顾客从进门到结账。再加性能测试：一万人同时下单会不会卡死。找出的问题叫 bug（菜咸了），修它叫 debug。

    留下什么

    测试用例、bug 清单、测试报告。

    最常翻车

    「没时间了，测试砍掉。」等于不试菜直接开业，第一桌客人就是你的试菜员。

  5. 5
    开业→

    部署上线

    deployment / release
    餐厅里

    把做好的一切搬进正式铺面，挂招牌，开门。聪明的店会先「试营业」：只请亲友和熟客，没问题了再登广告。

    软件里

    把代码放到正式服务器上，让真实用户能用。常用灰度发布 canary release：先放给 1% 的用户，没事再 10%、100%。出大问题立刻回滚 rollback：撤掉新菜，换回昨天的版本。这一套现在多由自动流水线完成，叫 CI/CD。

    留下什么

    线上可访问的版本、发布记录、回滚方案。

    最常翻车

    周五晚上全量上线然后下班。行业里有句老话：周五不发版。

  6. 6
    天天经营→

    运维与监控

    operations
    餐厅里

    开业不是结束，是开始。每天进货、盘点、修灶台、看监控、处理投诉、防火防盗。

    软件里

    盯着服务器不宕机、磁盘不满、接口不变慢。看日志查问题，靠监控告警半夜被叫醒，定期备份数据，补安全漏洞。做这些的人叫运维 Ops，现在常和开发合称 DevOps。

    留下什么

    监控大盘、告警规则、备份、故障复盘报告。

    最常翻车

    没有备份。仓库烧了才想起来账本没抄一份放别处。

  7. 7
    换季菜单、翻新→

    迭代维护

    maintenance / iteration
    餐厅里

    顾客说太咸就调，夏天上凉菜，三年后重新装修。一家店的大部分寿命都在这个阶段。

    软件里

    收集反馈、修 bug、加功能、升级那些外购的「半成品」、淘汰没人用的功能，然后回到第 1 站重新分析需求。软件七成以上的总成本，花在上线之后。

    留下什么

    新版本（v1.1、v2.0……）、更新日志 changelog。

    最常翻车

    以为「做完了」。软件没有做完，只有停止维护。

第 7 站走完，回到第 1 站。这样绕一圈，就叫一次迭代。

店里都有谁

七站不是一个人走完的。餐厅里的每个岗位，软件团队里都有对应的人。小团队一人兼几职很正常，大公司则每个格子都是一个部门。

餐厅里软件团队里管什么
店长产品经理 PM决定做什么、不做什么、先做什么。
室内设计师、菜单设计设计师 UI / UX长什么样，顾客怎么走不会迷路。
厨师程序员 / 工程师 developer把东西做出来。前端、后端、数据库各有专精。
试菜员测试工程师 QA找出问题，拦在开业之前。
后勤、物业运维 Ops / DevOps水电不断、灶台不坏、半夜救火。
老板技术负责人 / 架构师 architect定大方向：开几间屋、用什么设备、哪些门一走就回不了头。

一次性大装修，还是边营业边改

瀑布 waterfall敏捷 agile
像什么一次性大装修。七站按顺序走完一遍，上一站全部结束才开下一站，像盖楼，图纸定了就不改。边营业边调整。两周一小圈（叫一个冲刺 sprint），每圈把七站快速走一遍，做出一点能用的东西给用户看，再调方向。
适合需求非常确定、改一步极贵的场景：银行核心系统、航天软件。需求还在变、要快速试错的场景：今天绝大多数互联网产品。
一句话：需求越模糊，越要敏捷；错一步越贵，越要瀑布。这又是一次权衡。

小白最容易踩的六个坑

误区「加个按钮很简单吧，半小时的事。」
真相按钮本身十分钟。按钮背后要新增接口、改数据库、写测试、兼容老版本，半小时变三天很正常。你看到的是前厅，改的是整家店。
误区「程序员就是修电脑的，或者就是敲代码的。」
真相敲代码占三成，剩下是理解需求、设计、排错、沟通。厨师的活也从来不只是颠勺。
误区「上线了就做完了。」
真相上线是开业，不是关门。软件大部分成本花在上线之后。
误区「多加几个人就能快一倍。」
真相十个厨师挤一个灶台只会更慢。软件业有条著名的定律：给已经延期的项目加人，会让它更延期。
误区「先做完整版再上线，别让用户看到半成品。」
真相憋大招最危险。先开小店试营业，让真实顾客告诉你哪道菜该留。
误区「出 bug 就是程序员水平差。」
真相任何足够复杂的系统都有 bug，就像任何餐厅都会偶尔上错菜。关键是发现得快不快、修得快不快、会不会再犯。

三十秒讲给别人听

复述版 软件是一家看不见的餐厅。前厅给顾客看，后厨真干活，仓库存东西，服务员按单子传话，水电煤是租来的服务器，付款和发短信找供应商。做软件就是开店：先想清楚开给谁，画好图纸，装修试做，试菜，试营业再开业，然后天天经营、不断换菜单。程序员脑子里最要紧的习惯是：把大事拆小，抓共性，提前想意外，接受取舍，别重复造轮子，先开小店试营业，永远站在顾客那边。
