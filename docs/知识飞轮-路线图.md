# 知识飞轮 · 迭代路线图 + 技术选型

> 版本：v1.0　制定：2026-08-28
> 定位：DailyWorkbench 从「看板」演进成「个人知识飞轮操作台」的**方向盘**。
> 关联：`TECH_CHARTER.md`（北极星与选型原则）、`知识库沉淀存储方案.md`（沉淀写入侧规范）、`adr/`。
> 性质：**活文档**。每完成一个 Phase 或改变选型，回来更新它；冗余条目定期删。

---

## 0 · 一句话

把工作台做成一个**「输入 → 捕获 → 沉淀 → 蒸馏 → 输出 → 复盘反哺」的知识飞轮**，
数据分**三层大脑**存放，**只让"捕获层"上云**，守住"零构建·零依赖·离线可跑"的北极星。

---

## 1 · 飞轮模型 · 三层大脑

```
 输入                捕获                沉淀 · 蒸馏               输出
┌────────┐        ┌────────┐        ┌──────────────┐        ┌────────┐
│ AI 资讯 │──┐     │ 灵感随记 │──┐     │ ① Obsidian    │──精炼──▶│ ③ ima  │
│ up 主内容│  ├───▶│ 文章剪藏 │  ├───▶│  本地草稿/工作库│        │ 最终大脑│
└────────┘  │     │ up主蒸馏 │  │     │（kbSave 已通） │        └────────┘
            │     └────────┘  │     └──────┬───────┘
            │        ▲        │            │
            │        │  ② Supabase 云端薄收件箱（多端捕获暂存，
            │        └────────┘   PC 后端定期"抽干"→归进 Obsidian）
            │
            └───────────── 复盘反哺（发现缺口 → 定向找输入）◀────────────┘
```

**三层大脑各司其职：**

| 层 | 是什么 | 存什么 | 谁是权威 |
|---|---|---|---|
| ① Obsidian 本地库 | 用户内容的**工作/草稿库** | 沉淀、蒸馏卡、复盘、灵感（消化后） | **权威副本** |
| ② Supabase 云收件箱 | **跨设备的暂存中转** | 只放"还没消化的捕获小数据" | 临时，抽干即归 ① |
| ③ ima 最终大脑 | 人工闸门的**长期知识库** | Obsidian 里打磨成熟的精炼版 | 人工导入，纯文件交接 |

**核心取舍（为什么这么分）**
- **云不当主库、只当收件箱**：不把 Obsidian 整个搬上云——那会推翻本地库、是大**单向门**。只让"捕获层"上云，云端存的是"原料"，消化完就沉回本地。这是满足"多端/手机/备份"诉求的**最小云依赖**，不违背离线北极星。
- **ima 纯文件交接**：ima（腾讯）无开放写 API，不做 API 集成；工作台把精炼版归到 `待入ima/` 文件夹，用户手动导入 ima。ima 出开放 API 再重估。

## 2 · 技术选型定论表

> 写法沿用 `TECH_CHARTER.md`：每格带"门性/何时重估"，多数是双向门（错了随时改），少数单向门（写 ADR 再动）。

| 层 | 定论 | 门性 / 何时重估 |
|---|---|---|
| 用户内容权威副本 | **Obsidian md**（`/api/kb/save` + `kbSave`，已通） | 双向门；本地库不再够用才动 |
| 云端收件箱 | **复用已有 Supabase**，单表 `capture_inbox`（jsonb 存捕获小数据）；**不引新中间件**(YAGNI) | schema=**单向门→ADR**；同步频率/抽干策略=双向门 |
| 备份兜底 | Obsidian 库 + 工作台数据 **git 自动提交**（复用 self-hosted runner） | 双向门 |
| 前端本地态 | localStorage 当**离线草稿 + 未同步缓存**（乐观本地写 → 后台推云） | 双向门 |
| ima 接入 | **纯文件交接**（`待入ima/` 手动导入），不做 API 集成 | ima 出开放 API 再重估 |

**为什么云端复用 Supabase 而非另起炉灶**：宪章已把 Supabase 认证为"唯一云依赖"（现只存模型配置），扩一张表当收件箱是**边际成本最低**的选择；Postgres 有 REST/RLS，手机可直连，且不新增一个需要长期维护的中间件（对照 `design-principles` 卡 4「一上来就想引入中间件」）。

## 3 · 四阶段路线图

> 排序原则：**先本地做扎实、可逆的先做、代价小的先做**；把牵扯最广的"手机全功能"压到最后。每阶段标【代价】【门】。

### Phase 1 · up 主经验蒸馏库（先跑通 · 纯本地 · 零云）✅ 已完成（2026-08-31）
**代价：低 ｜ 门：双向门**
把小红书/B站/文章的经验沉淀成**可检索、可复用的"经验卡库"**。复用 `creator-video-decoder`/`video-cangjie-distill`/`baoyu-url-to-markdown` skill 的产出，结构化成经验卡，经 `kbSave` 落 Obsidian 新模块 `蒸馏库/`，配浏览/筛选视图。**不碰云。**
> 详见 `.claude/plan/phase1-蒸馏库.md`。

### Phase 2 · 本地持久化做扎实 + 备份兜底
**代价：低-中 ｜ 门：双向门**
- **每日灵感"随手记 + 留存"**：localStorage 即时存（离线可记）+ 一份 `kbSave` 到 Obsidian `灵感/YYYY-MM-DD/`（日粒度追加）。补上"记录每日灵感"缺口。
- **Obsidian 库纳入 git 自动备份**：复用 self-hosted runner，定期提交 Obsidian 库（或其子集）到私有仓，兑现"数据安全/备份兜底"。

### Phase 3 · 云端薄收件箱 + 多端实时同步
**代价：中 ｜ 门：含单向门（schema）→ 先写 ADR**
- Supabase 建 `capture_inbox`（jsonb + 设备标识 + 消化状态 + 时间戳）。
- 前端捕获走**"乐观本地 + 后台推云"**：先写 localStorage 立即可见，再异步推 Supabase；离线则排队、联网补推。
- PC 后端**定时"抽干收件箱 → 归进 Obsidian"**（消化后标记/清理云端记录）。
- 手机联网即同步、离线也能记。**这步兑现"多端实时同步"。**
- ⚠️ 动 `capture_inbox` 结构前，先在 `docs/adr/` 写一条 ADR（云端收件箱数据契约＝单向门，参照宪章"单向门清单"与 `design-principles` 卡 12）。

### Phase 4 · 手机全功能 + 出口闭环（压轴）
**代价：中-高 ｜ 门：较大门**
- **手机全功能**：手机也能 AI 对话 / 剪藏 / 蒸馏——经收件箱中转，不依赖 PC 开机。（牵扯把 `/api/*` 能力搬到云或安全暴露，是本路线图最大的门，故压最后。）
- **出口闭环**：工作台「一键归拢到 `待入ima/`」——把选定的精炼笔记复制/汇集到导出文件夹，用户手动导入 ima。
- **复盘反哺**：复盘视图聚合本周捕获/蒸馏/灵感，生成"该深挖什么"，让飞轮转起来。

## 4 · 阶段依赖与"先决门"

```
Phase 1（蒸馏库·本地）──┐
Phase 2（灵感留存·备份）─┼──▶ Phase 3（云收件箱·多端同步, 需 ADR）──▶ Phase 4（手机全功能·出口闭环）
                        │           ▲
              两者互不依赖，可并行     └─ Supabase 表契约是单向门，务必先 ADR
```

- Phase 1、2 互不依赖、都纯本地，可任意先后 / 并行。
- Phase 3 是"上云"的**第一道单向门**，必须先 ADR。
- Phase 4 依赖 Phase 3 的收件箱通道。

---

## 5 · 不做什么（YAGNI 边界）

- **不**把 Obsidian 整库搬上云；**不**用云端当主库。
- **不**为 ima 做 API 集成（它没有开放写 API）。
- **不**在没触到"多端/手机"真实需求前提前建云表（Phase 1-2 一律本地）。
- **不**引入除 Supabase 外的新中间件（消息队列、独立数据库、后端框架）——除非某 Phase 真触到瓶颈并在此表登记重估。
